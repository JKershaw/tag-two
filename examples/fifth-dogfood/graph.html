243: Why this exists
244: 
245: Modern coding agents are remarkably capable when given a well-defined task.
246: 
247: The harder problem is deciding what should be done next.
248: 
249: Real projects are rarely a queue of perfectly specified independent tickets. An objective may require research before implementation. Research may reveal new work. Tasks may depend on other tasks. Some questions require humans. Some approaches fail. Priorities change as evidence accumulates.
250: 
251: "tag-two" explores a simple idea:
252: 
253: Represent that evolving understanding as a persistent graph, and let agents help investigate and evolve it.
254: 
255: The graph is not primarily a backlog.
256: 
257: It is the system's current model of the problem.

262: 
263: Start with an objective:
264:

266:

268:

289:     ↓

291:     ↓

313:

391: Research before decomposition
392: 
393: One of the strongest lessons from the original TAG experiment is that decomposition quality depends on research quality.
394: 
395: A model shown a handful of arbitrary source excerpts will tend to generate work related to those excerpts.
396: 
397: That is not necessarily the same as work important to the objective.
398: 
399: For example, an objective such as:
400: 
401: «Improve TAG»
402: 
403: previously produced locally plausible tasks involving protocol fields, validation edge cases and CLI parsing.
404: 
405: Those tasks were not necessarily wrong.
406: 
407: The problem was that the system had insufficient understanding to know whether they mattered.
408: 
409: Therefore:
410: 
411: Do not confuse code inspection with understanding the objective.
412: 
413: Before decomposing a broad objective, an agent should be able to investigate enough context to understand:
414: 
415: 1. what the project is trying to achieve;
416: 2. what currently exists;
417: 3. what currently works;
418: 4. what has already been attempted;
419: 5. what important uncertainties remain;
420: 6. what would constitute meaningful progress.
421: 
422: The agent should use normal repository tools where possible:
423: 
424: - read files;
425: - search;
426: - inspect documentation;
427: - inspect tests;
428: - inspect relevant history;
429: - run safe/read-only commands where appropriate.
430: 
431: Do not recreate a coding agent's repository exploration abilities by manually assembling arbitrary source excerpts unless there is a demonstrated reason to do so.

502: 
503: Different graph nodes may eventually benefit from different models.
504: 
505: For example:
506: 
507: - decomposition may favour concise instruction-following;
508: - difficult implementation may favour a strong coding model;
509: - summarisation may use a cheap model;
