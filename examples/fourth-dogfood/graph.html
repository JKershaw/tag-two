171: Why this exists
172: 
173: Modern coding agents are remarkably capable when given a well-defined task.
174: 
175: The harder problem is deciding what should be done next.
176: 
177: Real projects are rarely a queue of perfectly specified independent tickets. An objective may require research before implementation. Research may reveal new work. Tasks may depend on other tasks. Some questions require humans. Some approaches fail. Priorities change as evidence accumulates.
178: 
179: "tag-two" explores a simple idea:
180: 
181: Represent that evolving understanding as a persistent graph, and let agents help investigate and evolve it.
182: 
183: The graph is not primarily a backlog.
184: 
185: It is the system's current model of the problem.

190: 
191: Start with an objective:
192:

194:

196:

208: └── Demonstrate the improvement

215: 
216: objective
217:     ↓
218: investigate
219:     ↓
220: graph
221:     ↓
222: choose useful work
223:     ↓

225:     ↓

240: The hypothesis
241: 
242: A useful agent system does not necessarily need one enormous autonomous context.
243: 
244: Instead, it can maintain durable external state describing:
245: 
246: - what we are trying to achieve;
247: - what we currently believe;
248: - what has been discovered;
249: - what remains uncertain;
250: - what work is available;
251: - what depends on what;
252: - what has already happened;
253: - where a human is required.
254: 
255: Agents can then operate on bounded pieces of that state.
256: 
257: This potentially allows different agents, models, tools and humans to collaborate without requiring a single continuous conversation.
258:

319: Research before decomposition
320: 
321: One of the strongest lessons from the original TAG experiment is that decomposition quality depends on research quality.
322: 
323: A model shown a handful of arbitrary source excerpts will tend to generate work related to those excerpts.
324: 
325: That is not necessarily the same as work important to the objective.
326: 
327: For example, an objective such as:
328: 
329: «Improve TAG»
330: 
331: previously produced locally plausible tasks involving protocol fields, validation edge cases and CLI parsing.
332: 
333: Those tasks were not necessarily wrong.
334: 
335: The problem was that the system had insufficient understanding to know whether they mattered.
336: 
337: Therefore:
338: 
339: Do not confuse code inspection with understanding the objective.
340: 
341: Before decomposing a broad objective, an agent should be able to investigate enough context to understand:
342: 
343: 1. what the project is trying to achieve;
344: 2. what currently exists;
345: 3. what currently works;
346: 4. what has already been attempted;
347: 5. what important uncertainties remain;
348: 6. what would constitute meaningful progress.
349: 
350: The agent should use normal repository tools where possible:
351: 
352: - read files;
353: - search;
354: - inspect documentation;
355: - inspect tests;
356: - inspect relevant history;
357: - run safe/read-only commands where appropriate.
358: 
359: Do not recreate a coding agent's repository exploration abilities by manually assembling arbitrary source excerpts unless there is a demonstrated reason to do so.
