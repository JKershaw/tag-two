5: ## Run the seed
6: 
7: Requires Node.js 22+ and Git. There are no package dependencies or build step.
8: From a Git repository's root, set `OPENROUTER_API_KEY` in your environment (never
9: in a tracked file), then run:
10: 
11: ```sh
12: node /absolute/path/to/tag-two/bin/tag.js plan "Make tag-two better at achieving its purpose."
13: ```
14: 
15: An optional final argument selects another repository root. To use the shorter
16: `tag plan "objective"` command, run `npm link` in the tag-two checkout first.
17: Run the offline tests with `npm test` in that checkout.
18: 
19: The planner uses one OpenRouter model, `deepseek/deepseek-chat-v3-0324`, with
20: read-only tools to list/read/search tracked text files and inspect recent commit
21: subjects. The model chooses what to investigate; no source excerpts are selected
22: in advance. Add new source files to Git before planning. It cannot execute shell
23: commands, run tests, modify source, or work on the proposed tasks. Its claims about
24: what works are therefore explicitly unverified unless repository evidence supports them.
25: 
26: **Data boundary:** the objective and model-requested repository content are sent to
27: OpenRouter and its model provider. Use only repositories you are authorized to
28: share. Untracked files, common credential paths, symlinks, binary files and files
29: larger than 256 KiB are excluded; these filters are not a secret detector. Review
30: tracked content for embedded secrets before using the planner.
31: 
32: After investigation, open `.tag/graph.html` directly in a browser. It shows the
33: objective, research summary, task reasons and evidence, linked dependencies,
34: ready/blocked tasks, and the tool results behind the plan. `.tag/graph.json` is the
35: durable, provider-independent graph; its `run` field records model provenance,
36: reported cost (or null when unavailable), and investigation history.
37: 
38: The graph is a proposal, not an execution queue: “ready” means no graph dependencies,
39: and a human decides what happens next. Nothing runs automatically afterward.
40: Both outputs stay local and are Git-ignored because they may include repository
41: content. Existing `.tag` directories are never overwritten: preserve or move a
42: previous experiment explicitly before starting another.
43: 
44: The seed allows at most ten model requests, 4,096 output tokens per request and
45: 80,000 serialized request bytes. It checks model pricing and caps provider prices
46: at $0.50/million input tokens and $1.50/million output tokens, with no per-request
47: fee. At these limits, even conservatively counting each request byte as an input
48: token leaves the run below $1 (roughly $0.47 before small protocol overhead).
49: Unavailable models, higher prices, network errors, exhausted limits or invalid
50: graphs stop the run without automatic retries, JSON repair or fabricated tasks.
51: An output write failure can leave a partial `.tag` directory; inspect it before
52: moving it aside.
53: 
54: The first dogfood run should use the objective above exactly once. Inspect its
55: unedited graph for usefulness rather than rerunning until the answer looks good.

59: Why this exists
60: 
61: Modern coding agents are remarkably capable when given a well-defined task.
62: 
63: The harder problem is deciding what should be done next.
64: 
65: Real projects are rarely a queue of perfectly specified independent tickets. An objective may require research before implementation. Research may reveal new work. Tasks may depend on other tasks. Some questions require humans. Some approaches fail. Priorities change as evidence accumulates.
66: 
67: "tag-two" explores a simple idea:
68: 
69: Represent that evolving understanding as a persistent graph, and let agents help investigate and evolve it.
70: 
71: The graph is not primarily a backlog.
72: 
73: It is the system's current model of the problem.
74: 
75: ---
76: 
77: The core idea
78: 
79: Start with an objective:
80: 
81: «Improve tag-two.»
82: 
83: An agent investigates the relevant repository and problem using its normal tools.
84: 
85: It then constructs a small graph representing useful next work:
86: 
87: Improve tag-two
88: │
89: ├── Understand current behaviour
90: │
91: ├── Investigate an important uncertainty
92: │
93: ├── Improve a demonstrated weakness
94: │   └── depends on investigation
95: │
96: └── Demonstrate the improvement
97: 
98: The graph persists independently of any model conversation.
99: 
100: Later, a node can be investigated or worked on by another agent. Its result changes the graph.
101: 
102: Over time:
103: 
104: objective
105:     ↓
106: investigate
107:     ↓
108: graph
109:     ↓
110: choose useful work
111:     ↓
112: agent works
113:     ↓
114: observe result
115:     ↓
116: update graph
117:     ↓
118: repeat
119: 
120: Initially, humans may perform some of those transitions manually.
121: 
122: That is intentional.
123: 
124: The experiment is to gradually discover which parts are useful to automate rather than designing the complete autonomous system in advance.
125:

127: 
128: The hypothesis
129: 
130: A useful agent system does not necessarily need one enormous autonomous context.
131: 
132: Instead, it can maintain durable external state describing:
133: 
134: - what we are trying to achieve;
135: - what we currently believe;
136: - what has been discovered;
137: - what remains uncertain;
138: - what work is available;
139: - what depends on what;
140: - what has already happened;
141: - where a human is required.
142: 
143: Agents can then operate on bounded pieces of that state.
144: 
145: This potentially allows different agents, models, tools and humans to collaborate without requiring a single continuous conversation.
146: 
147: The persistent graph is the continuity.

206: 
207: Research before decomposition
208: 
209: One of the strongest lessons from the original TAG experiment is that decomposition quality depends on research quality.
210: 
211: A model shown a handful of arbitrary source excerpts will tend to generate work related to those excerpts.
212: 
213: That is not necessarily the same as work important to the objective.
214: 
215: For example, an objective such as:
216: 
217: «Improve TAG»
218: 
219: previously produced locally plausible tasks involving protocol fields, validation edge cases and CLI parsing.
220: 
221: Those tasks were not necessarily wrong.
222: 
223: The problem was that the system had insufficient understanding to know whether they mattered.
224: 
225: Therefore:
226: 
227: Do not confuse code inspection with understanding the objective.
228: 
229: Before decomposing a broad objective, an agent should be able to investigate enough context to understand:
230: 
231: 1. what the project is trying to achieve;
232: 2. what currently exists;
233: 3. what currently works;
234: 4. what has already been attempted;
235: 5. what important uncertainties remain;
236: 6. what would constitute meaningful progress.
237: 
238: The agent should use normal repository tools where possible:
239: 
240: - read files;
241: - search;
242: - inspect documentation;
243: - inspect tests;
244: - inspect relevant history;
245: - run safe/read-only commands where appropriate.
246: 
247: Do not recreate a coding agent's repository exploration abilities by manually assembling arbitrary source excerpts unless there is a demonstrated reason to do so.
248:

250: 
251: Agents are capabilities, not the state
252: 
253: An agent may be:
254: 
255: - a hosted coding agent;
256: - a model accessed through an API;
257: - a local model;
258: - a human;
259: - another orchestration system.
260: 
261: The graph should not depend on the conversational memory of any particular agent.
262: 
263: A fresh agent should be able to understand the relevant work from durable project state plus whatever repository/environment access it is given.
264: 
265: This means:
266: 
267: «Worker handoffs may be stateless. Durable project understanding cannot be.»
268:

270:

276:

296: 
297: Bounded agent work
298: 
299: Agents should usually receive bounded work.
300: 
301: A useful pattern is:
302: 
303: inspect
304: → perform one meaningful action
305: → report what happened
306: → update durable state
307: → stop
308: 
309: Avoid agents implicitly continuing through an unlimited chain of work merely because more work is available.
310: 
311: This makes behaviour easier to understand, review and recover.
312: 
313: The appropriate boundaries should emerge through experimentation rather than being specified completely now.

316: 
317: Model choice
318: 
319: Different graph nodes may eventually benefit from different models.
320: 
321: For example:
322: 
323: - decomposition may favour concise instruction-following;
324: - difficult implementation may favour a strong coding model;
325: - summarisation may use a cheap model;
326: - research may require stronger reasoning or larger context.
327: 
328: Do not build model routing yet.
329: 
330: Start with one model/agent that works.
331: 
332: Model selection becomes part of the system only when there is evidence that it provides meaningful value.
333: 
334: One lesson from the original TAG experiment was that stronger reasoning is not automatically better for every operation.
335: 
336: A reasoning-heavy model repeatedly exhausted a structured planning output budget before producing valid JSON. Disabling reasoning for that bounded structured-planning call produced a valid graph using substantially fewer output tokens.
337: 
338: The broader lesson is:
339: 
340: Use model capability appropriate to the operation rather than simply maximising reasoning effort.

467: Bootstrap rule
468: 
469: Every iteration should make the next useful iteration less manual.
470: 
471: That is the path toward self-hosting.
472: 
473: For example:
474:

477: 
478: Iteration 1
479: human → graph node → agent → result → human updates graph

482: human → graph node → agent → result → system updates graph
483:
