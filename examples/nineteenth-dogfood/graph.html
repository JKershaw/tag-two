5: ## Run the seed
6: 
7: Requires Node.js 22+ and Git. There are no package dependencies or build step.
8: From a Git repository's root, set `OPENROUTER_API_KEY` in your environment (never
9: in a tracked file), then run:
10: 
11: ```sh
12: node /absolute/path/to/tag-two/bin/tag.js plan "Make tag-two better at achieving its purpose."
13: ```
14: 
15: An optional final argument selects another repository root. To use the shorter
16: `tag plan "objective"` command, run `npm link` in the tag-two checkout first.
17: Run the offline tests with `npm test` in that checkout.
18: 
19: The planner uses one OpenRouter model, `deepseek/deepseek-chat-v3-0324`, with
20: read-only tools to list/read/search tracked text files and inspect recent commit
21: subjects. `read_file` returns a whole file in one call, bounded at 40,000
22: characters; anything longer reports the exact line to resume from. The model chooses what to investigate; no source excerpts are selected
23: in advance. Add new source files to Git before planning. It cannot execute shell
24: commands, run tests, modify source, or work on the proposed tasks. Its claims about
25: what works are therefore explicitly unverified unless repository evidence supports them.
26: 
27: **Data boundary:** the objective and model-requested repository content are sent to
28: OpenRouter and its model provider. Use only repositories you are authorized to
29: share. Untracked files, common credential paths, symlinks, binary files and files
30: larger than 256 KiB are excluded; these filters are not a secret detector. Review
31: tracked content for embedded secrets before using the planner.
32: 
33: After investigation, open `.tag/graph.html` directly in a browser. It shows the
34: objective, research summary, task reasons and evidence, linked dependencies,
35: ready/blocked tasks, and the tool results behind the plan. `.tag/graph.json` is the
36: durable, provider-independent graph; its `run` field records model provenance,
37: reported cost (or null when unavailable), and investigation history.
38: 
39: The graph is a proposal, not an execution queue: “ready” means no graph dependencies,
40: and a human decides what happens next. Nothing runs automatically afterward.
41: 
42: When a node has been worked, record what happened against it:
43: 
44: ```sh
45: node /absolute/path/to/tag-two/bin/tag.js record graph/graph.json expand-tools "what happened"
46: ```
47: 
48: `record` appends a timestamped outcome and re-renders the HTML beside the graph. It
49: chooses nothing, runs nothing and calls no model; a human still decides which node to
50: work and does the work. Outcomes accumulate rather than replace, so a claim and its
51: later correction sit side by side, and a node that has any is shown as worked.
52: 
53: Outcomes are held on the graph rather than on the node, as
54: `{node, title, at, outcome}`. Node ids do not survive replanning — the seventh run's
55: ids and the fourteenth's have nothing in common — and an outcome is evidence about
56: work that really happened, so it must outlive whichever node happened to propose it.
57: 
58: When a later run produces a better graph for the same objective, adopt it:
59: 
60: ```sh
61: node /absolute/path/to/tag-two/bin/tag.js adopt .tag/graph.json graph/graph.json
62: ```
63: 
64: `adopt` replaces the durable graph wholesale and carries every recorded outcome
65: across, refusing a graph that answers a different objective. Outcomes whose node no
66: longer exists are kept and shown separately rather than discarded. The new graph's
67: investigation transcript is left behind with the archived run and referenced by path,
68: because a durable graph larger than one `read_file` call cannot be read by the planner
69: it is supposed to inform.
70: 
71: To see what a run actually did, without opening a browser or calling a model:
72: 
73: ```sh
74: node /absolute/path/to/tag-two/bin/tag.js observe .tag/graph.json
75: ```
76: 
77: `observe` reads a saved graph or a `failed-run.json` and reports the model, request
78: count, cost, which tools were called and which were never called, which files were read
79: whole and which came back truncated, and — for a graph — every evidence citation naming
80: a file that run never opened. It was written after fourteen runs had been assessed by
81: hand with throwaway scripts asking the same questions.
82: 
83: The next run is then given those outcomes. Not the graph — only the outcomes, and only
84: after it has read a file. Handed whole nodes up front, two real runs restated them
85: verbatim and stopped investigating. For the same reason the durable graph and its HTML
86: are hidden from the planner's own file tools: a run that read `graph/graph.json` as an
87: ordinary tracked file copied node bodies and their citations straight out of it. Every
88: other file in that directory is still listed.
89: 
90: [`graph/graph.json`](graph/graph.json) is this repository's own working graph, tracked
91: rather than left in the ignored `.tag` directory so that tag-two's understanding of its
92: own problem is durable, inspectable and readable by the planner.
93: Committing a graph is a deliberate exception for this repository, which is its own
94: experimental subject; `plan()` still ignores `.tag` by default because graphs of other
95: repositories may contain their content. The working graph carries no investigation
96: transcript: every run is archived unedited in `examples/`, and an 83 KB duplicate
97: inside a tracked file would on its own consume most of the planner's research budget.
98: Both outputs stay local and are Git-ignored via a generated `.tag/.gitignore`,
99: including when planning in another repository, because they may include repository
100: content. Existing `.tag` directories are never overwritten: preserve or move a
101: previous experiment explicitly before starting another.
102: 
103: The seed allows at most eight model requests, 4,096 output tokens per request and
104: 160,000 serialized request bytes. The byte budget has been the binding constraint in
105: every run and no run has ever used more than five requests, so the third rise in that
106: budget was paid for by lowering the request limit from ten, leaving the worst-case cost
107: bound unchanged. It checks model pricing and caps provider prices
108: at $0.50/million input tokens and $1.50/million output tokens, with no per-request
109: fee. At these limits, even conservatively counting each request byte as an input
110: token leaves the run below $1 (roughly $0.68 before small protocol overhead).
111: Observed runs cost well under a cent.
112: Unavailable models, higher prices, network errors, exhausted limits or invalid
113: graphs stop the run without automatic retries, JSON repair or fabricated tasks.
114: A matched markdown fence around the answer is removed before parsing, which is an
115: envelope, not repair: malformed JSON, prose around the JSON, a drifted objective and
116: any invalid graph are still rejected. A run that fails after investigating anything
117: writes `.tag/failed-run.json` with the transcript, the raw answer, the request count
118: and the reported cost, and keeps the directory so the failure can be diagnosed.
119: An output write failure can leave a partial `.tag` directory; inspect it before
120: moving it aside.

122: The first dogfood run should use the objective above exactly once. Inspect its
123: unedited graph for usefulness rather than rerunning until the answer looks good.

132: Why this exists
133: 
134: Modern coding agents are remarkably capable when given a well-defined task.
135: 
136: The harder problem is deciding what should be done next.
137: 
138: Real projects are rarely a queue of perfectly specified independent tickets. An objective may require research before implementation. Research may reveal new work. Tasks may depend on other tasks. Some questions require humans. Some approaches fail. Priorities change as evidence accumulates.
139: 
140: "tag-two" explores a simple idea:
141: 
142: Represent that evolving understanding as a persistent graph, and let agents help investigate and evolve it.
143: 
144: The graph is not primarily a backlog.
145: 
146: It is the system's current model of the problem.
147: 
148: ---
149: 
150: The core idea
151: 
152: Start with an objective:
153: 
154: «Improve tag-two.»
155: 
156: An agent investigates the relevant repository and problem using its normal tools.
157: 
158: It then constructs a small graph representing useful next work:
159: 
160: Improve tag-two
161: │
162: ├── Understand current behaviour
163: │
164: ├── Investigate an important uncertainty
165: │
166: ├── Improve a demonstrated weakness
167: │   └── depends on investigation
168: │
169: └── Demonstrate the improvement
170: 
171: The graph persists independently of any model conversation.
172: 
173: Later, a node can be investigated or worked on by another agent. Its result changes the graph.
174: 
175: Over time:
176: 
177: objective
178:     ↓
179: investigate
180:     ↓
181: graph
182:     ↓
183: choose useful work
184:     ↓
185: agent works
186:     ↓
187: observe result
188:     ↓
189: update graph
190:     ↓
191: repeat
192: 
193: Initially, humans may perform some of those transitions manually.
194: 
195: That is intentional.
196: 
197: The experiment is to gradually discover which parts are useful to automate rather than designing the complete autonomous system in advance.

201: The hypothesis
202: 
203: A useful agent system does not necessarily need one enormous autonomous context.
204: 
205: Instead, it can maintain durable external state describing:
206: 
207: - what we are trying to achieve;
208: - what we currently believe;
209: - what has been discovered;
210: - what remains uncertain;
211: - what work is available;
212: - what depends on what;
213: - what has already happened;
214: - where a human is required.
215: 
216: Agents can then operate on bounded pieces of that state.
217: 
218: This potentially allows different agents, models, tools and humans to collaborate without requiring a single continuous conversation.
219: 
220: The persistent graph is the continuity.

280: Research before decomposition
281: 
282: One of the strongest lessons from the original TAG experiment is that decomposition quality depends on research quality.
283: 
284: A model shown a handful of arbitrary source excerpts will tend to generate work related to those excerpts.
285: 
286: That is not necessarily the same as work important to the objective.
287: 
288: For example, an objective such as:
289: 
290: «Improve TAG»
291: 
292: previously produced locally plausible tasks involving protocol fields, validation edge cases and CLI parsing.
293: 
294: Those tasks were not necessarily wrong.
295: 
296: The problem was that the system had insufficient understanding to know whether they mattered.
297: 
298: Therefore:
299: 
300: Do not confuse code inspection with understanding the objective.
301: 
302: Before decomposing a broad objective, an agent should be able to investigate enough context to understand:
303: 
304: 1. what the project is trying to achieve;
305: 2. what currently exists;
306: 3. what currently works;
307: 4. what has already been attempted;
308: 5. what important uncertainties remain;
309: 6. what would constitute meaningful progress.
310: 
311: The agent should use normal repository tools where possible:
312: 
313: - read files;
314: - search;
315: - inspect documentation;
316: - inspect tests;
317: - inspect relevant history;
318: - run safe/read-only commands where appropriate.
319: 
320: Do not recreate a coding agent's repository exploration abilities by manually assembling arbitrary source excerpts unless there is a demonstrated reason to do so.
