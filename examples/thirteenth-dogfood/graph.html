5: ## Run the seed
6: 
7: Requires Node.js 22+ and Git. There are no package dependencies or build step.
8: From a Git repository's root, set `OPENROUTER_API_KEY` in your environment (never
9: in a tracked file), then run:
10: 
11: ```sh
12: node /absolute/path/to/tag-two/bin/tag.js plan "Make tag-two better at achieving its purpose."
13: ```
14: 
15: An optional final argument selects another repository root. To use the shorter
16: `tag plan "objective"` command, run `npm link` in the tag-two checkout first.
17: Run the offline tests with `npm test` in that checkout.
18: 
19: The planner uses one OpenRouter model, `deepseek/deepseek-chat-v3-0324`, with
20: read-only tools to list/read/search tracked text files and inspect recent commit
21: subjects. `read_file` returns a whole file in one call, bounded at 40,000
22: characters; anything longer reports the exact line to resume from. The model chooses what to investigate; no source excerpts are selected
23: in advance. Add new source files to Git before planning. It cannot execute shell
24: commands, run tests, modify source, or work on the proposed tasks. Its claims about
25: what works are therefore explicitly unverified unless repository evidence supports them.
26: 
27: **Data boundary:** the objective and model-requested repository content are sent to
28: OpenRouter and its model provider. Use only repositories you are authorized to
29: share. Untracked files, common credential paths, symlinks, binary files and files
30: larger than 256 KiB are excluded; these filters are not a secret detector. Review
31: tracked content for embedded secrets before using the planner.
32: 
33: After investigation, open `.tag/graph.html` directly in a browser. It shows the
34: objective, research summary, task reasons and evidence, linked dependencies,
35: ready/blocked tasks, and the tool results behind the plan. `.tag/graph.json` is the
36: durable, provider-independent graph; its `run` field records model provenance,
37: reported cost (or null when unavailable), and investigation history.
38: 
39: The graph is a proposal, not an execution queue: “ready” means no graph dependencies,
40: and a human decides what happens next. Nothing runs automatically afterward.
41: 
42: When a node has been worked, record what happened against it:
43: 
44: ```sh
45: node /absolute/path/to/tag-two/bin/tag.js record graph/graph.json expand-tools "what happened"
46: ```
47: 
48: `record` appends a timestamped outcome to that one node, revalidates the graph and
49: re-renders the HTML beside it. It chooses nothing, runs nothing and calls no model; a
50: human still decides which node to work and does the work. Outcomes accumulate rather
51: than replace, and a node that has any is shown as worked rather than ready.
52: 
53: [`graph/graph.json`](graph/graph.json) is this repository's own working graph — the
54: seventh run's output, promoted out of the ignored `.tag` directory so that tag-two's
55: understanding of its own problem is durable, tracked and readable by the planner.
56: Committing a graph is a deliberate exception for this repository, which is its own
57: experimental subject; `plan()` still ignores `.tag` by default because graphs of other
58: repositories may contain their content. The working graph carries no investigation
59: transcript: the unedited seventh run including its transcript is archived in
60: [`examples/seventh-dogfood/graph.json`](examples/seventh-dogfood/graph.json), and an
61: 83 KB duplicate inside a tracked file would on its own consume most of the planner's
62: research budget.
63: Both outputs stay local and are Git-ignored via a generated `.tag/.gitignore`,
64: including when planning in another repository, because they may include repository
65: content. Existing `.tag` directories are never overwritten: preserve or move a
66: previous experiment explicitly before starting another.
67: 
68: The seed allows at most ten model requests, 4,096 output tokens per request and
69: 120,000 serialized request bytes. It checks model pricing and caps provider prices
70: at $0.50/million input tokens and $1.50/million output tokens, with no per-request
71: fee. At these limits, even conservatively counting each request byte as an input
72: token leaves the run below $1 (roughly $0.66 before small protocol overhead).
73: Observed runs cost well under a cent.
74: Unavailable models, higher prices, network errors, exhausted limits or invalid
75: graphs stop the run without automatic retries, JSON repair or fabricated tasks.
76: A matched markdown fence around the answer is removed before parsing, which is an
77: envelope, not repair: malformed JSON, prose around the JSON, a drifted objective and
78: any invalid graph are still rejected. A run that fails after investigating anything
79: writes `.tag/failed-run.json` with the transcript, the raw answer, the request count
80: and the reported cost, and keeps the directory so the failure can be diagnosed.
81: An output write failure can leave a partial `.tag` directory; inspect it before
82: moving it aside.
83: 
84: The first dogfood run should use the objective above exactly once. Inspect its
85: unedited graph for usefulness rather than rerunning until the answer looks good.
86: 
87: The complete dogfood experiment log — every run against this repository, what it
88: showed, and what it ruled out — is in [`EXPERIMENTS.md`](EXPERIMENTS.md). It was
89: split out of this file after it grew past the planner's whole-file read limit and a
90: real run investigated a truncated README.

93: 
94: Why this exists
95: 
96: Modern coding agents are remarkably capable when given a well-defined task.
97: 
98: The harder problem is deciding what should be done next.
99: 
100: Real projects are rarely a queue of perfectly specified independent tickets. An objective may require research before implementation. Research may reveal new work. Tasks may depend on other tasks. Some questions require humans. Some approaches fail. Priorities change as evidence accumulates.
101: 
102: "tag-two" explores a simple idea:
103: 
104: Represent that evolving understanding as a persistent graph, and let agents help investigate and evolve it.
105: 
106: The graph is not primarily a backlog.
107: 
108: It is the system's current model of the problem.
109: 
110: ---
111: 
112: The core idea
113: 
114: Start with an objective:
115: 
116: «Improve tag-two.»
117: 
118: An agent investigates the relevant repository and problem using its normal tools.
119: 
120: It then constructs a small graph representing useful next work:
121: 
122: Improve tag-two
123: │
124: ├── Understand current behaviour
125: │
126: ├── Investigate an important uncertainty
127: │
128: ├── Improve a demonstrated weakness
129: │   └── depends on investigation
130: │
131: └── Demonstrate the improvement
132: 
133: The graph persists independently of any model conversation.
134: 
135: Later, a node can be investigated or worked on by another agent. Its result changes the graph.
136: 
137: Over time:
138: 
139: objective
140:     ↓
141: investigate
142:     ↓
143: graph
144:     ↓
145: choose useful work
146:     ↓
147: agent works
148:     ↓
149: observe result
150:     ↓
151: update graph
152:     ↓
153: repeat
154: 
155: Initially, humans may perform some of those transitions manually.
156: 
157: That is intentional.
158: 
159: The experiment is to gradually discover which parts are useful to automate rather than designing the complete autonomous system in advance.
160: 
161: ---
162: 
163: The hypothesis
164: 
165: A useful agent system does not necessarily need one enormous autonomous context.
166: 
167: Instead, it can maintain durable external state describing:
168: 
169: - what we are trying to achieve;
170: - what we currently believe;
171: - what has been discovered;
172: - what remains uncertain;
173: - what work is available;
174: - what depends on what;
175: - what has already happened;
176: - where a human is required.
177: 
178: Agents can then operate on bounded pieces of that state.
179: 
180: This potentially allows different agents, models, tools and humans to collaborate without requiring a single continuous conversation.
181: 
182: The persistent graph is the continuity.
183: 
184: ---
185: 
186: The most important principle
187: 
188: The graph is the product.
189: 
190: Internal state is only useful if a human can understand it.
191: 
192: At every meaningful stage we should be able to inspect the graph and answer:
193: 
194: - What is the objective?
195: - What does the system currently think needs doing?
196: - Why?
197: - What has it learned?
198: - What is runnable now?
199: - What is blocked?
200: - What depends on something else?
201: - Where is human input required?
202: - What changed recently?
203: 
204: A JSON representation may be the durable format.
205: 
206: It must not be the primary human interface.
207: 
208: Even a crude HTML representation is preferable if it makes the system understandable at a glance.
209:

211: 
212: What a node represents
213: 
214: A node represents a meaningful part of the system's understanding of the problem.
215: 
216: A node may eventually represent things such as:
217: 
218: - work;
219: - investigation;
220: - a question;
221: - evidence;
222: - a decision;
223: - an outcome.
224:

226:

228: 
229: For example:
230:

241: 
242: Research before decomposition
243: 
244: One of the strongest lessons from the original TAG experiment is that decomposition quality depends on research quality.
245: 
246: A model shown a handful of arbitrary source excerpts will tend to generate work related to those excerpts.
247: 
248: That is not necessarily the same as work important to the objective.
249: 
250: For example, an objective such as:
251: 
252: «Improve TAG»
253: 
254: previously produced locally plausible tasks involving protocol fields, validation edge cases and CLI parsing.
255: 
256: Those tasks were not necessarily wrong.
257: 
258: The problem was that the system had insufficient understanding to know whether they mattered.
259: 
260: Therefore:
261: 
262: Do not confuse code inspection with understanding the objective.
263: 
264: Before decomposing a broad objective, an agent should be able to investigate enough context to understand:
265: 
266: 1. what the project is trying to achieve;
267: 2. what currently exists;
268: 3. what currently works;
269: 4. what has already been attempted;
270: 5. what important uncertainties remain;
271: 6. what would constitute meaningful progress.
272: 
273: The agent should use normal repository tools where possible:
274: 
275: - read files;
276: - search;
277: - inspect documentation;
278: - inspect tests;
279: - inspect relevant history;
280: - run safe/read-only commands where appropriate.
281: 
282: Do not recreate a coding agent's repository exploration abilities by manually assembling arbitrary source excerpts unless there is a demonstrated reason to do so.
283: 
284: ---
285: 
286: Agents are capabilities, not the state
287: 
288: An agent may be:
289: 
290: - a hosted coding agent;
291: - a model accessed through an API;
292: - a local model;
293: - a human;
294: - another orchestration system.
295: 
296: The graph should not depend on the conversational memory of any particular agent.
297: 
298: A fresh agent should be able to understand the relevant work from durable project state plus whatever repository/environment access it is given.
299: 
300: This means:
301: 
302: «Worker handoffs may be stateless. Durable project understanding cannot be.»
303: 
304: The graph owns continuity.
305: 
306: Agents temporarily contribute reasoning or work.
307: 
308: ---
309: 
310: Human involvement is normal
311: 
312: Human intervention is not a failure mode.
313: 
314: Especially during bootstrap, a human may:
315: 
316: - choose which node to work next;
317: - reject a poor decomposition;
318: - answer a question;
319: - approve a risky action;
320: - select an agent or model;
321: - inspect an outcome;
322: - decide whether evidence is sufficient.
323: 
324: If an agent lacks a permission or capability, surface that boundary.
325: 
326: Do not silently invent workarounds merely to preserve the appearance of autonomy.
327: 
328: The goal is useful orchestration, not maximum autonomy.
329: 
330: ---
331: 
332: Bounded agent work
333: 
334: Agents should usually receive bounded work.
335: 
336: A useful pattern is:
337: 
338: inspect
339: → perform one meaningful action
340: → report what happened
341: → update durable state
342: → stop
343: 
344: Avoid agents implicitly continuing through an unlimited chain of work merely because more work is available.
345: 
346: This makes behaviour easier to understand, review and recover.
347: 
348: The appropriate boundaries should emerge through experimentation rather than being specified completely now.
349: 
350: ---
351: 
352: Model choice
353: 
354: Different graph nodes may eventually benefit from different models.
355: 
356: For example:
357: 
358: - decomposition may favour concise instruction-following;
359: - difficult implementation may favour a strong coding model;
360: - summarisation may use a cheap model;
361: - research may require stronger reasoning or larger context.
362: 
363: Do not build model routing yet.
364: 
365: Start with one model/agent that works.
366: 
367: Model selection becomes part of the system only when there is evidence that it provides meaningful value.
368: 
369: One lesson from the original TAG experiment was that stronger reasoning is not automatically better for every operation.
370: 
371: A reasoning-heavy model repeatedly exhausted a structured planning output budget before producing valid JSON. Disabling reasoning for that bounded structured-planning call produced a valid graph using substantially fewer output tokens.
372: 
373: The broader lesson is:
374: 
375: Use model capability appropriate to the operation rather than simply maximising reasoning effort.
376:

378: 
379: Cost
380: 
381: Cost matters, particularly if graphs eventually create many agent calls.
382: 
383: But cost optimisation is not the first experiment.
384: 
385: First establish that the system produces useful work.
386: 
387: Then measure.
388: 
389: Then optimise.
390: 
391: Cheap and free models are interesting because sufficiently bounded graph nodes may allow smaller models to perform useful work.
392:

502: Bootstrap rule
503: 
504: Every iteration should make the next useful iteration less manual.
505: 
506: That is the path toward self-hosting.
507: 
508: For example:
509: 
510: Iteration 0
511: human → objective → agent → graph → human
512: 
513: Iteration 1
514: human → graph node → agent → result → human updates graph
515: 
516: Iteration 2
517: human → graph node → agent → result → system updates graph
518: 
519: Iteration 3
520: system suggests next node → human approves → agent works
521: 
522: Iteration 4
523: system handles bounded low-risk work itself
524: 
525: This sequence is illustrative, not a roadmap.
526: 
527: Do not implement later iterations until the previous behaviour exists and teaches us something.
