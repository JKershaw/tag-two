20: read-only tools to list/read/search tracked text files and inspect recent commit
21: subjects. `read_file` returns a whole file in one call, bounded at 40,000
22: characters; anything longer reports the exact line to resume from. The model chooses what to investigate; no source excerpts are selected

29: share. Untracked files, common credential paths, symlinks, binary files and files
30: larger than 256 KiB are excluded; these filters are not a secret detector. Review
31: tracked content for embedded secrets before using the planner.

410: anything or execute anything; a human still chooses the node and does the work. The
411: first thing recorded through it was the refutation above, against the very node that
412: caused it.
413: 
414: Committing a graph is a deliberate exception for this repository, which is its own
415: experimental subject. `plan()` still ignores `.tag` by default, because graphs of
416: other people's repositories may contain their content.
417: 
418: Note what this makes true, and what it does not. tag-two is now part of the causal
419: loop of its own development: the choice of what to work came out of its graph, and the
420: result of that work went back into its graph rather than only into a human's notes. It
421: is not autonomous, it did not judge anything, and `plan()` still cannot read a graph
422: back — it can only write a new one. The next question is what happens when the
423: planner investigates a repository that contains a graph with a refuted node in it.
424: 
425: ---
426: 
427: Why this exists
428: 
429: Modern coding agents are remarkably capable when given a well-defined task.
430: 
431: The harder problem is deciding what should be done next.
432: 
433: Real projects are rarely a queue of perfectly specified independent tickets. An objective may require research before implementation. Research may reveal new work. Tasks may depend on other tasks. Some questions require humans. Some approaches fail. Priorities change as evidence accumulates.
434: 
435: "tag-two" explores a simple idea:
436: 
437: Represent that evolving understanding as a persistent graph, and let agents help investigate and evolve it.
438: 
439: The graph is not primarily a backlog.
440: 
441: It is the system's current model of the problem.
442: 
443: ---
444: 
445: The core idea
446: 
447: Start with an objective:
448: 
449: «Improve tag-two.»
450: 
451: An agent investigates the relevant repository and problem using its normal tools.
452: 
453: It then constructs a small graph representing useful next work:
454: 
455: Improve tag-two
456: │
457: ├── Understand current behaviour
458: │
459: ├── Investigate an important uncertainty
460: │
461: ├── Improve a demonstrated weakness
462: │   └── depends on investigation
463: │
464: └── Demonstrate the improvement
465: 
466: The graph persists independently of any model conversation.
467: 
468: Later, a node can be investigated or worked on by another agent. Its result changes the graph.
469: 
470: Over time:
471: 
472: objective
473:     ↓
474: investigate
475:     ↓
476: graph
477:     ↓
478: choose useful work
479:     ↓
480: agent works
481:     ↓
482: observe result
483:     ↓
484: update graph
485:     ↓
486: repeat
487: 
488: Initially, humans may perform some of those transitions manually.
489: 
490: That is intentional.
491: 
492: The experiment is to gradually discover which parts are useful to automate rather than designing the complete autonomous system in advance.
493: 
494: ---
495: 
496: The hypothesis
497: 
498: A useful agent system does not necessarily need one enormous autonomous context.
499: 
500: Instead, it can maintain durable external state describing:
501: 
502: - what we are trying to achieve;
503: - what we currently believe;
504: - what has been discovered;
505: - what remains uncertain;
506: - what work is available;
507: - what depends on what;
508: - what has already happened;
509: - where a human is required.
510: 
511: Agents can then operate on bounded pieces of that state.
512: 
513: This potentially allows different agents, models, tools and humans to collaborate without requiring a single continuous conversation.
514: 
515: The persistent graph is the continuity.
516: 
517: ---
518: 
519: The most important principle
520: 
521: The graph is the product.
522: 
523: Internal state is only useful if a human can understand it.
524: 
525: At every meaningful stage we should be able to inspect the graph and answer:
526: 
527: - What is the objective?
528: - What does the system currently think needs doing?
529: - Why?
530: - What has it learned?
531: - What is runnable now?
532: - What is blocked?
533: - What depends on something else?
534: - Where is human input required?
535: - What changed recently?
536: 
537: A JSON representation may be the durable format.
538: 
539: It must not be the primary human interface.
540: 
541: Even a crude HTML representation is preferable if it makes the system understandable at a glance.
542: 
543: ---
544: 
545: What a node represents
546: 
547: A node represents a meaningful part of the system's understanding of the problem.
548: 
549: A node may eventually represent things such as:
550: 
551: - work;
552: - investigation;
553: - a question;
554: - evidence;
555: - a decision;
556: - an outcome.
557: 
558: Do not build an elaborate type system until the implementation needs one.
559: 
560: For the first version, a node can be extremely small.
561: 
562: For example:
563: 
564: {
565:   "id": "research-current-behaviour",
566:   "title": "Understand current planning behaviour",
567:   "reason": "We need evidence about the current behaviour before changing it.",
568:   "dependsOn": []
569: }
570: 
571: Add fields only when a demonstrated use case requires them.
572: 
573: ---
574: 
575: Research before decomposition
576: 
577: One of the strongest lessons from the original TAG experiment is that decomposition quality depends on research quality.
578: 
579: A model shown a handful of arbitrary source excerpts will tend to generate work related to those excerpts.
580: 
581: That is not necessarily the same as work important to the objective.
582: 
583: For example, an objective such as:
584: 
585: «Improve TAG»
586: 
587: previously produced locally plausible tasks involving protocol fields, validation edge cases and CLI parsing.
588: 
589: Those tasks were not necessarily wrong.
590: 
591: The problem was that the system had insufficient understanding to know whether they mattered.
592: 
593: Therefore:
594: 
595: Do not confuse code inspection with understanding the objective.
596: 
597: Before decomposing a broad objective, an agent should be able to investigate enough context to understand:
598: 
599: 1. what the project is trying to achieve;
600: 2. what currently exists;
601: 3. what currently works;
602: 4. what has already been attempted;
603: 5. what important uncertainties remain;
604: 6. what would constitute meaningful progress.
605: 
606: The agent should use normal repository tools where possible:
607: 
608: - read files;
609: - search;
610: - inspect documentation;
611: - inspect tests;
612: - inspect relevant history;
613: - run safe/read-only commands where appropriate.
614: 
615: Do not recreate a coding agent's repository exploration abilities by manually assembling arbitrary source excerpts unless there is a demonstrated reason to do so.
616: 
617: ---
618: 
619: Agents are capabilities, not the state
620: 
621: An agent may be:
622: 
623: - a hosted coding agent;
624: - a model accessed through an API;
625: - a local model;
626: - a human;
627: - another orchestration system.
628: 
629: The graph should not depend on the conversational memory of any particular agent.
630: 
631: A fresh agent should be able to understand the relevant work from durable project state plus whatever repository/environment access it is given.
632: 
633: This means:
634: 
635: «Worker handoffs may be stateless. Durable project understanding cannot be.»
636: 
637: The graph owns continuity.
638: 
639: Agents temporarily contribute reasoning or work.
640: 
641: ---
642: 
643: Human involvement is normal
644: 
645: Human intervention is not a failure mode.
646: 
647: Especially during bootstrap, a human may:
648: 
649: - choose which node to work next;
650: - reject a poor decomposition;
651: - answer a question;
652: - approve a risky action;
653: - select an agent or model;
654: - inspect an outcome;
655: - decide whether evidence is sufficient.
656: 
657: If an agent lacks a permission or capability, surface that boundary.
658: 
659: Do not silently invent workarounds merely to preserve the appearance of autonomy.
660: 
661: The goal is useful orchestration, not maximum autonomy.
662: 
663: ---
664: 
665: Bounded agent work
666: 
667: Agents should usually receive bounded work.
668: 
669: A useful pattern is:
670: 
671: inspect
672: → perform one meaningful action
673: → report what happened
674: → update durable state
675: → stop
676: 
677: Avoid agents implicitly continuing through an unlimited chain of work merely because more work is available.
678: 
679: This makes behaviour easier to understand, review and recover.
680: 
681: The appropriate boundaries should emerge through experimentation rather than being specified completely now.
682: 
683: ---
684: 
685: Model choice
686: 
687: Different graph nodes may eventually benefit from different models.
688: 
689: For example:
690: 
691: - decomposition may favour concise instruction-following;
692: - difficult implementation may favour a strong coding model;
693: - summarisation may use a cheap model;
694: - research may require stronger reasoning or larger context.
695: 
696: Do not build model routing yet.
697: 
698: Start with one model/agent that works.
699: 
700: Model selection becomes part of the system only when there is evidence that it provides meaningful value.
701: 
702: One lesson from the original TAG experiment was that stronger reasoning is not automatically better for every operation.
703: 
704: A reasoning-heavy model repeatedly exhausted a structured planning output budget before producing valid JSON. Disabling reasoning for that bounded structured-planning call produced a valid graph using substantially fewer output tokens.
705: 
706: The broader lesson is:
707: 
708: Use model capability appropriate to the operation rather than simply maximising reasoning effort.
709: 
710: ---
711: 
712: Cost
713: 
714: Cost matters, particularly if graphs eventually create many agent calls.
715: 
716: But cost optimisation is not the first experiment.
717: 
718: First establish that the system produces useful work.
719: 
720: Then measure.
721: 
722: Then optimise.
723: 
724: Cheap and free models are interesting because sufficiently bounded graph nodes may allow smaller models to perform useful work.
725: 
726: That is a hypothesis worth testing later.
727: 
728: Do not compromise the initial demonstration merely to make it free.
729: 
730: ---
731: 
732: What we learned from the original TAG
733: 
734: An earlier implementation explored many of these ideas.
735: 
736: It included concepts such as:
737: 
738: - persistent graph state;
739: - graph revisions;
740: - generations;
741: - structured graph mutations;
742: - strict proposal validation;
743: - controller/worker separation;
744: - execution limits;
745: - token and cost accounting;
746: - model allowlists;
747: - provider routing;
748: - research-context construction;
749: - worker packages;
750: - acceptance gates;
751: - persistent history;
752: - HTML graph rendering.
753: 
754: Many of those ideas may eventually be useful.
755: 
756: They are not requirements for tag-two.
757: 
758: The original experiment taught us that it is easy to build sophisticated orchestration machinery before proving that the central loop is useful.
759: 
760: Several experiments became dominated by debugging the orchestration infrastructure itself:
761: 
762: - model availability;
763: - provider routing;
764: - reasoning-token behaviour;
765: - output-token ceilings;
766: - strict JSON proposal validation;
767: - research-context selection;
768: - controller-state transport;
769: - protocol/status compatibility.
770: 
771: Meanwhile the question we actually cared about was much simpler:
772: 
773: «Can the system investigate an objective and produce a useful graph that we can see?»
774: 
775: "tag-two" starts again from that question.
